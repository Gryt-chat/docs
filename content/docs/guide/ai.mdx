## The short version

Gryt is built by one person, so some AI assistance is the difference between shipping and not shipping. It also means there's nobody around to catch my mistakes, so I'd rather write the rule down than decide case by case at midnight.

The rule:

- **Gryt's foundation is hand-written.** The SFU, the authentication and identity code, and anything that parses untrusted input. I write all of it by hand and intend to keep doing that.
- **The tools built on top of it may be AI-assisted.** Documentation, the marketing site, interface code, dev tooling.
- **Anything that can affect security is reviewed by hand before it's published**, whichever category it came from.

AI is not used to change core functionality.

## Never AI-generated

Everything in these areas is written by hand:

| Area | Path | Why |
|------|------|-----|
| SFU / media plane | `packages/sfu` | WebRTC, RTP forwarding, ICE, SVC layer selection. Everything else depends on it. |
| Server auth & crypto | `packages/server/src/auth`, `src/middleware` | Challenge-response authentication, JWT validation, token handling. |
| Identity service | `packages/auth` | The certificate authority that ties public keys to Gryt identities. |
| Client identity & keys | `packages/client/src/packages/common/src/auth/` | Where your keypair is generated and stored on your device. |
| Image processing | `packages/image-worker` | Decodes untrusted uploads. Image parsing has a long history of memory-safety bugs. |
| Server data layer | `packages/server/src/db`, `src/storage` | Persistence and object storage. |

The image worker probably looks out of place on that list. It compresses avatars and generates thumbnails, which isn't high-stakes work. But it takes a file someone else uploaded and hands it to a decoder, so it handles untrusted input, and I treat it as core.

## May be AI-assisted

- **Documentation** — including this page
- **The marketing site and blog** — `packages/site`
- **Interface and presentation code** — components, styling, layout in `packages/client`, but not the auth files listed above
- **Dev tooling and ops scripts** — `ops/`, build scripts, CI configuration
- **Tests, type definitions, and refactors that don't change behaviour**

The split comes down to how much damage a mistake can do. A wrong paragraph in the docs means someone gets confused and opens an issue. A wrong certificate check means someone gets impersonated.

<Callout type="info">
Interface code is on this list, but the client's authentication files are not. `identity-keys.ts`, `identity-certificate.ts`, `keycloak.ts`, `electron-auth.ts` and `account-api.ts` live inside the client, and they're hand-written like the rest of the foundation.
</Callout>

## What this policy is not about

Gryt ships **RNNoise**, a neural network that removes background noise from your microphone. It runs locally on your device and never sends audio anywhere.

That's a different thing from what this page covers. This policy is about who writes Gryt's code, not about which algorithms the code uses. RNNoise is a feature, and the integration around it is hand-written like the rest of the client's audio pipeline.

So "AI is not used to change core functionality" means no model writes the SFU or the auth code. It doesn't mean Gryt refuses to ship useful machine learning where it helps.

## How to verify this

Every commit that had AI assistance carries a `Co-Authored-By` trailer naming the model, so you can check this rather than take my word for it:

```bash
git log --format='%H %s%n%(trailers:key=Co-Authored-By)'
```

If you find that trailer on a commit touching one of the paths in the table above, that's a mistake on my part, and I'd like to know. Open an issue.

## For contributors

The same rules apply to contributions, with one addition: say so.

**You must:**

- Tick the AI-assisted box in the pull request template if any part of your patch was AI-generated or AI-assisted
- Keep AI out of the paths listed in the table above

**What happens then:**

- Non-core AI-assisted contributions get reviewed normally
- Contributions to core or security-relevant paths are expected to be hand-written. If an AI-assisted patch touches them, I'll either ask you to rewrite it or rewrite it myself before it lands
- Undisclosed AI-generated code in a core path is grounds for closing the PR

This isn't meant to make contributing feel adversarial. Disclosure just tells me how closely to read.

## This policy can change

Gryt is still in early development and my thinking on this will probably shift as the tooling does. The principle underneath it won't: the parts of Gryt that can hurt you if they're wrong are written by a person who understands them.

If the policy changes, it changes here, in a commit you can read.
